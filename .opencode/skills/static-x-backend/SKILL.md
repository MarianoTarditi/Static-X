## Activation Contract

Use for Static-X backend design, implementation, and review. Read the full [backend guide](../../../Docs/Guia_Backend_Senior_NET_Capas.md) before backend design or coding; use it for details not overridden below.

## Hard Rules

- The approved manual Student payment slice adds BLL `DTOs/Payments`, `IPaymentService`/`PaymentService`, `PaymentProfile`; DAL entity-based `IPaymentRepository`/`PaymentRepository`; Entity payment/tariff models and monotonic ficha payment revision; API staff/self payment controllers and live coverage middleware. Preserve ARS integer cents, immutable effective-date tariffs and ledger, transaction-owned gym mutex, revision-bound protected previews and persisted idempotency. Latest-only audited void restores prior coverage; payments never reactivate accounts/fichas or grant global tenant access. Only concrete self/security actions may opt out of the default live Student coverage gate. Follow `Docs/Payments.md`; do not fabricate historical payments or apply migrations without separate authorization. This explicitly extends the DTO/profile inventories below without changing layer rules.

- Precedence: explicit user decisions override this skill and conflicting guide instructions. Preserve the authorized **four physical traditional projects** under `src/Static_X.{API,BLL,DAL,Entity}` and tests under `tests/Static_X.Tests`, registered in `Static-X.sln`. Do not introduce Clean/Onion, CQRS, handlers, or new layers.
- Enforce API → BLL → DAL → Entity. Allow BLL/API → Entity and API → DAL for composition. Never allow DAL → BLL/API or BLL → API. BLL consumes DAL repository interfaces, not implementations or DbContext.
- Put BLL services in `Services`, all service contracts in `Interfaces`; DAL repositories in `Repositories/Interfaces` and `Repositories/Implementations`, context/migrations in `Persistence`, and outboxes in `Persistence/Models`. API owns `Auth`, `Controllers`, scoped activation/recovery hosted workers in `Integrations`, and `Integrations/Email` implementing the separate BLL email-sender contracts. Password recovery actions belong to `AuthenticationController`, business operations to `IAccountService`/`AccountService`, and all persistence (including dispatcher cleanup/leases) to `IAccountRepository`/`AccountRepository`; do not split them into separate recovery controllers/services/repositories. Retain the independent recovery dispatcher, worker and email transport. Password recovery uses its own request-bound 30-minute Identity provider/outbox and never reuses activation tokens or contracts.
- For all future API controllers, use an explicit public constructor, store injected dependencies in private readonly fields, and assign them with `this.field = parameter;`, following `ActivationController`. Do not use primary constructors or migrate existing controllers outside the explicitly requested scope.
- Put all specific HTTP/business DTOs in BLL `DTOs/{Accounts,Activations,Gyms,Students}`, one conventional class per file with explicit properties and constructors. Preserve JSON, DataAnnotations, defaults, and nullability. Public business services consume DTO field groups and return DTOs, never entities, even in nested results; BLL maps entities and validates independently of MVC. Keep trusted gym/target identifiers, authorized roles, and cancellation separate; client DTO fields never authorize membership/roles. Do not wrap simple identifiers, enums, scalar results, or cancellation-only operations artificially. API owns transport validation/status mapping, not business entity mapping; preserve explicit Identity/auth/composition access to `IdentityAccount` and role enums. Keep framework errors, entities and internal Entity-owned `ActivationDelivery` in their existing layers; DAL remains entity-based, never referencing BLL DTOs.
- Scope tenant-owned reads and writes to their gym using trusted server-side identity/membership. Never accept a client-supplied gym ID alone as authorization; prevent cross-gym access, including indirect references and updates. The authorized exception is global `SuperAdmin = 4`, with `GymId = null` enforced by a database check constraint and unique filtered global email index. Only that role can provision gyms and reissue pending GymAdmin invitations over CSRF-protected HTTP. It has no implicit student-data access. Global login omits/nulls `gymId`, never searches tenants, and `/me`/cookie validation enforce persisted scope and role. Keep tenant role values 1–3. No fake gym, public global registration, startup bootstrap, activation CLI, local pickup, or operational terminal account-management interface is permitted. First SuperAdmin provisioning is a separately approved direct Development database operation, not shipped code. This supersedes historical CLI references.
- Put AutoMapper profiles in BLL `Mappings`, one per actual responsibility. API composition registers once with a BLL profile marker, scanning only BLL; only response-mapping services consume `IMapper`. Map persisted results through explicit DTO constructor parameters. Keep validation, normalization, trusted gym/role selection, and authorization in services, not profiles. Do not add automatic reverse/request/Identity response maps, controller mapping, DAL/Entity AutoMapper dependencies, or artificial activation profiles. Validate real profiles and preserve null/list behavior in tests. Keep `AutoMapper:LicenseKey` external (`AutoMapper__LicenseKey`), retain license diagnostics, and never assume production eligibility. Add concise Spanish XML summaries to mapping classes and constructors.
- AI may suggest routine changes; only a trainer can approve and apply them. Never auto-modify routines from AI output or treat suggestions as authorization.
- Entity owns pure `Account`/`AccountRole` and the explicitly authorized `IdentityAccount : IdentityUser` exception with an ASP.NET Core framework reference. Do not claim Entity is entirely framework-free or add EF/HTTP/provider coupling. `ActivationDelivery` belongs to Entity but is not an EF entity. Preserve existing CLR namespaces, migration IDs/Up/Down, mappings, Data Protection names, and HTTP contracts; use assembly/project-reference checks rather than namespaces as ownership evidence.
- Document every new or modified BLL service and DAL repository implementation with a concise, single-line Spanish XML `<summary>` immediately above the class and each method, including private helpers and explicit constructors when present. Explain verified responsibilities in neutral/professional Spanish; preserve existing security/operational comments and the language of unrelated comments and literals. Apply this language exception only to these summaries, without behavior changes or unrelated refactoring.
- The approved tenant invitation slice extends the existing activation service/repository, not gym provisioning: GymAdmin invites Trainer/Student; Trainer invites Student only; Student and global SuperAdmin cannot invoke tenant invitations. Student requires an explicitly selected existing active same-gym ficha. Persist pending identity, unique restrictive link, immutable `(GymId, Key)` request snapshot, expected-role invitation and outbox atomically; never infer/adopt an account from contact email. Existing ficha PATCH actions synchronize only explicitly linked Student login: deactivate disables and rotates stamps; reactivate restores only ficha-derived suspension, never administrative blocking, confirmation, password, lockout or old cookies. Disabled accounts cannot authenticate, activate, change/reset passwords or receive invitation delivery. This is the bounded approved exception to historical ficha-only state semantics. Preserve separate Account/IdentityAccount ownership and the existing recovery owners. The bounded Trainer list/state controls below are approved; login-email, role and profile editing remain deferred. See Docs/Students.md and Docs/ActivationOperations.md for rollout and guarded rollback.
- Keep Trainer list/deactivate/reactivate in `TrainersController` and existing account service/repository owners. Only GymAdmin may manage same-gym Trainer targets; independently validate actor/gym/pagination/opaque ID in BLL. List all states with safe Entity `TrainerAccountProjection`, DAL `TrainerAccountPage`, BLL account DTOs and explicit `AccountProfile` mapping. Reuse no-store metadata, global CSRF, existing tenant gym mutex and write-time Trainer/gym predicate. Disable rotates both stamps atomically; re-enable preserves the rotated security stamp; repeats preserve both. Never alter credentials, confirmation, lockout, links or Trainer `StudentAccessSuspended`, generate invitations, add a migration or grant global SuperAdmin tenant authority. Follow Docs/ActivationOperations.md for exact contracts and limits.

## Execution Steps

1. Inspect existing solution and relevant code before proposing changes; preserve unrelated structure.
2. Trace HTTP contract → BLL service interface → BLL implementation → DAL repository interface → DAL implementation → ENTITY model as applicable.
3. Validate transport in API, business rules and gym ownership in BLL, and integrity in storage. Use explicit DTOs, parameterized queries, async I/O, cancellation where appropriate, and consistent error handling without leaking internals or secrets.
4. Run `dotnet build "Static-X.sln"` and `dotnet test "Static-X.sln" --no-build`, including architecture/model checks, tenant isolation, global authorization, and HTTP/activation/worker regressions. Never use real SQL Server writes or Resend delivery as migration verification.

## Output Contract

Report affected divisions, decisions or assumptions, executed checks, and any unverified behavior. Do not claim tests passed unless run.
