# Static-X agent instructions

- The current architecture is the mandatory baseline for all future modules, entities, and classes. Apply the ownership and dependency rules below to every new change. Do not reopen settled layer decisions, move responsibilities between layers, or introduce architectural exceptions without explicit user approval. Treat [BackendArchitecture.md](Docs/BackendArchitecture.md) as the canonical architecture reference; any approved architecture change must update these instructions, the project skill, documentation, and applicable architecture checks together.
- For backend design, coding, or review, load the project-local [static-x-backend skill](.opencode/skills/static-x-backend/SKILL.md). It defines layering, gym isolation, and trainer-approved AI behavior.
- Read the full [backend guide](Docs/Guia_Backend_Senior_NET_Capas.md) before backend design or coding. Explicit user decisions and the project skill take precedence over conflicting guide architecture; do not implicitly reorganize the existing solution.
- The explicitly authorized physical architecture is `Static-X.sln`, with `src/Static_X.API`, `src/Static_X.BLL`, `src/Static_X.DAL`, `src/Static_X.Entity`, and `tests/Static_X.Tests`. Keep traditional references API → BLL → DAL → Entity; BLL/API may reference Entity directly, and API may reference DAL for composition. DAL must not reference BLL/API; BLL must not reference API. Do not introduce Clean/Onion, CQRS, handlers, or additional layers.
- Put BLL implementations in `Services` and all service contracts (including `IActivationEmailSender`) in `Interfaces`. DAL owns `Repositories/Interfaces`, `Repositories/Implementations`, and `Persistence` with `StaticXDbContext`, migrations, and the persistence-only `Models/ActivationOutbox`. API owns HTTP, `Auth`, composition, the scoped outbox hosted worker in `Integrations`, and external adapters in `Integrations/Email`. BLL consumes repository interfaces, never implementations or DbContext.
- The authorized global-account exception is `SuperAdmin = 4` with `GymId = null`; existing role numbers remain unchanged. Only SuperAdmin may have no gym, and tenant roles require a valid gym. Enforce this in storage and cookie validation, with a separate unique global normalized-email index. Global login omits/nulls `gymId`; a positive selector only searches that gym. Never fall back across tenants or authorize from request fields. SuperAdmin alone may provision gyms/reissue pending administrator invitations through CSRF-protected HTTP, and receives no implicit student/tenant-data access. No fake gym, public global signup, startup bootstrap, terminal account management, pickup transport, or activation CLI is permitted. The first SuperAdmin is provisioned directly into an explicitly confirmed Development database in a separately authorized secure operation, not by shipped application code. The HTTP host automatically dispatches persisted outbox mail using scoped services with cancellation and bounded delays; retain durable Data Protection keys/purposes and Resend guards. This explicitly supersedes historical CLI references. See `Docs/ActivationOperations.md`.
- BLL owns all specific HTTP/business request and response DTOs in `DTOs/{Accounts,Activations,Gyms,Students}`, alongside `Interfaces` and `Services`. Use one conventional class per file with explicit properties and constructors, preserving JSON, validation, defaults, and nullability. All applicable public business service contracts consume DTOs for input field groups and return DTOs instead of entities, including nested collections/results; BLL owns Entity-to-DTO mapping and independent business validation. Keep trusted gym/target identifiers, authorized roles, and cancellation separate from untrusted DTO fields; DTO gym/role values never authorize access. Simple identifiers, enums, scalar outcomes, and cancellation-only operations need no artificial DTO. API owns HTTP validation/status mapping, not business entity mapping; Identity/auth/composition may still use `GymAccount` and domain role enums. Keep framework error envelopes, domain entities, and the Entity-owned internal `ActivationDelivery` repository payload in their existing layers; DAL contracts remain entity-based and must never reference BLL DTOs.
- Entity owns `Entities` and `Enums`, including the deliberately coupled `GymAccount : IdentityUser` adapter. Its ASP.NET Core framework reference is an explicit exception solely for that adapter, not permission to introduce EF Core, providers, or HTTP contracts. `Account` remains the pure domain representation; `ActivationDelivery` is a non-persisted delivery payload.
- BLL owns AutoMapper profiles in `Mappings`, separated by actual responsibility (`StudentProfile`, `AccountProfile`, `GymProfile`). Register once in API composition, scanning only the BLL assembly through a profile marker. Inject `IMapper` only into services that map responses; keep validation, normalization, authorization, and trusted gym/role selection outside profiles. Preserve explicit DTO constructors and configure constructor parameters; map persisted repository results, not stale request values. Do not add automatic reverse/request-to-entity or `GymAccount` response maps, controller mapping, DAL/Entity AutoMapper dependencies, or artificial activation profiles. Keep the license key in external `AutoMapper:LicenseKey` configuration (`AutoMapper__LicenseKey` environment variable), never in source; do not suppress license diagnostics or assume production eligibility. Document mapping classes and constructors with concise Spanish XML summaries and validate real profiles in tests.
- Existing CLR namespaces are retained for compatibility, including legacy `DAL` namespaces on some Entity-owned types; namespace spelling is not assembly ownership. Verify actual project references and type assemblies. Preserve migration IDs/Up/Down, Identity table/index mappings, Data Protection purposes/application names, and HTTP contracts. See [physical architecture](Docs/BackendArchitecture.md).
- Run `dotnet build "Static-X.sln"` and `dotnet test "Static-X.sln" --no-build`, including architecture/model compatibility checks. Protect unrelated worktree edits; never apply database migrations or call Resend as migration verification.
- For future project code, use conventional class declarations with explicit properties and constructors instead of positional records or primary constructors. This style preference does not authorize a broad migration of existing declarations; change them only within explicitly requested scope and preserve required contracts and behavior.
- For all future API controllers, use an explicit public constructor, store injected dependencies in private readonly fields, and assign them with `this.field = parameter;`, following `ActivationController`. Do not use primary constructors or migrate existing controllers outside the explicitly requested scope.
- For all new or modified BLL services and DAL repository implementations, add a concise, single-line Spanish XML `<summary>` immediately above each class and every method (including private helpers and explicit constructors when present), explaining its actual responsibility in neutral/professional Spanish. This language exception applies only to these summaries; preserve existing security/operational comments and the language of unrelated comments and literals. This documentation preference does not authorize behavior changes or unrelated refactoring.
